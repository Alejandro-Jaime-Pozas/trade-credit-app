## The finding

The report's premise is a misconception, and naming it is most of the work: **there is no page
that creates custom field values.** `/labels` creates, renames and deletes the FIELDS. Typing a
new value on the credit case detail page already worked and already saved.

What did not work was the control admitting it. Yesterday's `ValueCombobox` lists the values
already in use, and a list of existing values reads as the set of permitted answers — so people
went hunting for the page that would let them add to it.

## What changed

**A `+ Create "…"` row at the foot of the list**, matching the customer search on
`/credit-cases/new` — the pattern this control was specified against in the first place.
Suppressed when the typed text already IS one of the values, compared case-insensitively:
offering "Create mty norte" beside an existing "MTY Norte" would invite the exact duplicate the
control exists to prevent.

**Yesterday's no-match fallback is gone.** Bug 4/1 made an unmatched search show the whole list
again, reasoning that an empty list reads as "invalid value". That concern was real; the create
row answers it directly and better. Keeping both would have buried the new row under every value
that does not match, which is precisely the row the user needs to see.

**The panel now opens for a field with no recorded values**, as soon as the user types. It used
to render a bare text box with no dropdown, and the empty field is exactly where "can I just type
one?" needs answering. The caret button still only appears when there is something to browse —
a caret promising an empty list is worse than none. Consequence: the input is now always
`role="combobox"`, since it always has a popup.

**A footer: "Added to this field when you save the case."** Custom fields save with the rest of
the Details section (4/1, item 4), so without it "Create" reads as a promise something was
written, and the user leaves the page having lost it.

**Placeholder "Pick or type a value"** so the affordance is visible before the dropdown is opened
at all.

The rows the arrow keys walk are now one list of tagged entries rather than options with a
special case bolted on, so Enter commits whatever is highlighted without the keyboard path
needing to know which kind of row it landed on.

## Tests worth noting

Two existing tests were rewritten rather than kept, because they pinned behaviour this fix
deliberately reverses — the no-match fallback, and the no-dropdown-when-empty case. Both are
called out above.

The reported bug is pinned end to end on the detail page, not only on the component: type a value
nobody has used, click Create, press Save, and `setLabelValue` is called with it.
