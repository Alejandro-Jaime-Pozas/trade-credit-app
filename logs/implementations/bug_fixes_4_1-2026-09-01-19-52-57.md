## Items 2 and 3 — arranging the dashboard's columns

One library, `lib/layoutPrefs.ts`, because the Details section needed the same thing. It is
pure, so the decisions that actually matter are unit-tested:

- **A saved order meets a list that changed.** An id no longer present is skipped (a deleted
  custom field would otherwise leave a phantom column); an id the saved order has never seen
  is appended. That second rule is what makes item 3's "a new custom field shows up as a new
  column at the end" true for a user who rearranged their columns months ago — their
  arrangement is honoured AND the new field is visible without them going looking for it.
- **A move takes the CURRENT order, not the stored one.** The stored order is allowed to be
  partial, so dropping onto a column the user has never touched has to work. The result is a
  complete order, which is also what makes the first drag in a fresh browser pin everything
  else down instead of letting the next render reshuffle around it.

Filters and sorts run over the VISIBLE columns only. A filter left active on a column the
user then hid would quietly remove rows with nothing on screen to explain why.

Two ways to rearrange, and the second is not a nicety: dragging is mouse-only, so without
Move up/Move down in the Columns menu a keyboard user could not reorder the table at all. The
menu is also the only way back for a hidden column — hiding it removes the header there was
to click. The last visible column cannot be switched off.

The CSV export follows the screen, hidden columns included, because it was already defined as
"what you are looking at".

## Item 4 — the Details section

It held three visual languages for one idea: read-only tiles (Customer, Days open), form
controls in a different shape, and a Custom fields panel further down the page. Now one list
of identical cards, each rendering a control or a `DetailValue` — the latter padded to match
a form control so a read-only value lines up with the inputs beside it instead of sitting a
few pixels higher, which is what made the old section read as two different kinds of thing.

Custom fields carry a blue `InfoTip` reading "Custom field". Drag handle per card rather than
the whole card, because a card containing a text input has to stay selectable.

**Custom field values joined the section's Save button.** This follows from "all fields look
the same": a per-card Save would have been the one thing in the section that did not. Knock-on
effects, all handled: `hasUnsavedChanges` counts changed custom fields (otherwise Discard sits
greyed out over a visibly changed box), Discard clears the drafts, and the case is re-read
after the label writes because the PATCH response was serialised before them and its
`custom_fields` is one step stale. An emptied box is still a delete rather than a save of `""`,
which would live on as a filterable empty option on the dashboard.

## Item 5 — the verdict deadline

The paragraph became a hover/focus `InfoTip`; it was making that one card twice the height of
every other. The placeholder now reads `7 (organization default)` instead of the words
"Organization default" — knowing a default exists is no help in deciding whether to override

## Item 1 — the value dropdown

A native `<datalist>` shows nothing until you type, so an organization's existing "MTY Norte"
was undiscoverable from the box; users retyped it, sometimes as "MTY norte", and the dashboard
then filtered the two as unrelated values. `ValueCombobox` lists every recorded value on click
or ArrowDown, narrows as you type, and stays a free-text input — the first case to use a new
value has to be able to type it. A field with no values yet renders no caret at all, since one
promising an empty list is worse than none.

One judgement call worth naming: typing something that matches nothing shows the whole list
again rather than an empty one. An empty list at that moment reads as "invalid value", which
is exactly wrong — a new value is the normal way a field gets its first entry.
