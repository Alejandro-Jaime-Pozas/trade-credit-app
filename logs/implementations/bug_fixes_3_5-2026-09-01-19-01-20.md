## Item 4 — Cancel writes nothing

The user's rule: *"cancel should literally allow user to cancel out without creating a request at
all."* That could not be done in the frontend alone. `GET /requirement-templates/{id}/impact/`
diffs the **stored** template against each open case, so there was nothing to diff until after
the write — which is why the page saved first and offered an undo.

`POST /requirement-templates/{id}/preview-impact/` diffs a **proposed** list instead. The
existing diff was extracted into `_diff_items_against_case`, keyed by file type id, and both
entry points now delegate to it — one implementation, so the preview cannot drift from the real
thing. `ProposedTemplateItem`'s defaults (`is_required=True`, `months_required=None`) mirror
exactly what `updateTemplateItems` sends, so the preview describes the save that would actually
happen.

The page now previews, holds the selection in `pendingFileTypeIds`, and writes only once the
user has answered. Cancel drops the held selection: no request, and the ticked boxes stay on
screen to keep adjusting. `previousFileTypeIds`, `handleCancelSave`'s revert, and the whole undo
path are gone.

## Item 2 — the Done prompt

Requirement edits on the credit case detail page were written per click, which left "Done"
meaning nothing and gave the user no way back. They are now a draft (`pendingAddIds` /
`pendingRemoveKeys`), rendered inline: dashed border, "Adding"/"Removing", and an Undo button.

Done with no queued edits closes the editor — no prompt, no request. Otherwise it previews what
making the drafted list the organization's default would do to the OTHER open cases and shows
`ImpactWarning` with three answers:

- **Update all** — writes the draft to this case, saves the list as the org default, applies it
  to the listed cases.
- **Only this case** — writes the draft to this case alone.
- **Cancel** — nothing, and the draft stays on screen.

The case being edited is filtered out of the preview entries: it is written directly either way,
so listing it would count it twice.

The per-row "Remove this required document?" confirmation was dropped. It was asking about
something that had not happened yet, and a queued removal is undoable right up until Done, which
is now the confirmation.

## Item 3 — relabelling runs the completion logic

`UploadDocumentViewSet` had `create` and `perform_destroy` but no `perform_update`, so a manual
relabel was the one path into the checklist that never recomputed the case: the UI read
"Complete" while the case sat in `missing_documents` for ever.

`perform_update` calls `handle_manual_requirement_change`, the same helper `perform_destroy`
uses and the right one — a person relabelling a document is a direct decision about one case, so
it may move the case forward *or* pull it back.

The previous credit case is read **before** the save: `credit_case` is a writable field, so one
PATCH can move a document between cases and un-complete one while completing the other. Both
ends are recomputed, deduplicated through a set.

## Item 1 — long document lists scroll

`DocumentList` caps at `SCROLL_AFTER = 6` documents and scrolls past that. Below the threshold
no scroll container is rendered at all, so a short list never gets a scrollbar it doesn't need.

The blocker was that the rows contain `FileTypeSelect`, whose dropdown was an absolutely-
positioned child — and a scroll container clips its descendants, so the panel would have been
sliced off on exactly the rows a user scrolls down to correct. That would have broken the
control item 3 is about. `FileTypeSelect` now renders its panel through a portal positioned
`fixed` against the trigger, copying `TableColumnHeader.tsx`, which solved the same problem for
the same reason. Its `onBlur` containment check had to go with it — the panel is no longer a
descendant, so focus moving into the search box read as "focus left"; document-level `mousedown`
and `focusin` listeners do that job now.

## Security note

`preview_impact` takes file type ids from a request body and reports on real credit cases, so
the ids are re-derived from `file_types_visible_to(request.user)` (globals plus the user's own
organization) rather than trusted, and unknown ids are rejected. That helper was extracted from
`FileTypeViewSet.get_queryset` so both answer "which file types exist for me" from one place —
two copies would be a tenant-isolation bug waiting to happen. The template itself is fetched
through `get_object()`, so another organization's template is a 404.
