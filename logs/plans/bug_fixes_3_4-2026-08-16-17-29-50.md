## Item 1 — success popups must disappear on their own

Today every "saved" confirmation is a `useState<string | null>` that stays on screen until
some other action happens to clear it. There are four of them:

| Page | State | Message |
| --- | --- | --- |
| `customers/[id]` | `saved` | "Saved." |
| `credit-cases/[id]` | `saved` | "Saved." |
| `requirements` | `saved` | "Default requirements saved…" (3 variants) |
| `credit-cases/new` | `customerSuccess` | `Customer "X" created successfully.` |

Deliberately NOT touched:

- **Error banners** — an error is something the user has to read and act on; a message
  that vanishes before it is read is worse than one that lingers.
- The green "✓ linked customer" panel on `credit-cases/new` — that is persistent state
  (which customer this case is for), not a confirmation popup.

### `frontend/src/lib/useTransientMessage.ts` (new)

One hook so all four behave identically:

```ts
const { message, show, clear } = useTransientMessage();
```

- `show(text)` displays the text and starts a `TRANSIENT_MESSAGE_MS` (4000ms) timer.
- Calling `show` again restarts the timer rather than stacking two.
- `clear()` hides it immediately and cancels the timer (used where the code already
  cleared the message — starting a new save, discarding changes, undoing).
- The timer id lives in a ref and is cancelled on unmount, so a fired timeout can never
  set state on an unmounted page.

The timeout is scheduled inside the `show` callback, never inside a `useEffect` —
`eslint-plugin-react-hooks`' `set-state-in-effect` rule errors on effect-driven state
updates and has bitten this repo before.

Tests: `frontend/src/lib/useTransientMessage.test.ts` with fake timers — appears, is gone
after the delay, re-showing restarts the clock, `clear` cancels, unmount cancels.

## Item 2 — uploaded documents can be renamed and deleted

### Backend

`UploadDocument.friendly_file_name` already exists on the model ("friendly file name for
readability") but is listed in the serializer's `read_only_fields`, so nothing can set it.

1. **`backend/storage/serializers.py`**
   - Drop `friendly_file_name` from `read_only_fields`.
   - Add `validate_friendly_file_name`: trim whitespace, and store a blank value as
     `None` rather than `""` so "cleared" is one thing in the database, not two.
   - `original_title` stays read-only: it is the evidence of what the customer actually
     sent, and the friendly name is a display label layered on top of it.

2. **`backend/storage/views.py` — `UploadDocumentViewSet.perform_destroy`**
   Deleting a document can un-satisfy a requirement, so the linked credit case's status
   has to be recomputed. Reuse `handle_manual_requirement_change` (already used when a
   user adds/removes a requirement by hand): it pulls a case waiting for a verdict back
   to `missing_documents` when something it needed is gone. Without this, deleting the
   only bank statement leaves a case sitting in "pending final verdict" that no longer
   has the documents it was advanced for.

   Multi-tenant: no new surface. `get_queryset()` already scopes to
   `customer__organization` OR `credit_case__customer__organization`, so PATCH and DELETE
   on another organization's document 404 before any of this runs.

3. **Tests** — `backend/storage/tests/views_serializers/test_document_rename_delete.py`
   - rename to a readable name succeeds and persists;
   - blank/whitespace-only rename clears it to null;
   - `original_title` is unaffected by a rename;
   - another organization's document cannot be renamed (404) or deleted (404), and still
     exists afterwards;
   - deleting a document deletes it;
   - deleting the document that satisfied the last requirement pulls the case back to
     `missing_documents`.

4. `./scripts/sync-api-schema.sh` — `friendly_file_name` is currently generated as
   `readonly` in `api.generated.ts`; regenerate so the frontend can send it.

### Frontend

5. **`frontend/src/components/DocumentList.tsx`**
   - Display name becomes `friendly_file_name || original_title`, so a renamed document
     shows its readable name everywhere it appears. The original file name is kept
     visible in the metadata line when a friendly name overrides it — the user still
     needs to know which file this actually is.
   - New optional props, matching the existing `onChangeFileType` convention (a control
     only appears when the page passes a handler for it):
     - `onRename?(document, friendlyName: string | null)` + `renamingUrl` for the
       in-flight row;
     - `onDelete?(document)` — the component only asks; the page owns the confirmation.
   - Rename is inline: a "Rename" button swaps the title for a text input with Save /
     Cancel, seeded with the current display name. Escape cancels, Enter saves.
     Submitting the unchanged name is a no-op rather than a pointless request.
   - Fire-and-forget, like `onChangeFileType`: the row shows a spinner while
     `renamingUrl` matches, and a failure surfaces in the page's error banner with the
     name reverting to what the server still holds.

6. **`credit-cases/[id]` and `customers/[id]`**
   - `handleRenameDocument` — PATCH `friendly_file_name`, update the row in place.
   - `handleDeleteDocument` — DELETE behind a `ConfirmDialog` (the pattern already used
     for customers, contacts and requirements; deletes need strict confirmation).
   - On the credit case page, deleting re-reads the case as well, because the backend may
     have moved its status back to "missing documents".

7. **Tests** — extend `frontend/src/components/DocumentList.test.tsx`: friendly name wins
   over the original title, rename opens/saves/cancels, an unchanged name fires nothing,
   Escape cancels, and Delete asks the page rather than deleting on its own.
