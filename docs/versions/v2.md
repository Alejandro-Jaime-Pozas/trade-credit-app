## Scope

Sized against what already exists in the codebase on 2026-08-31. Items moved out of this
list live in `docs/versions/v3.md` under "Moved out of v2", each with the reason.

### 1. Pagare expiry extraction  — BACKEND DONE 2026-08-31

- `pagare` is currently a PRESENCE-ONLY file type (it shares `PresenceOnlyPydantic`), so today
  the app records that a pagare exists and nothing else. Give it a real extraction model so
  `fecha_vencimiento` (the expiry / strike date) is pulled out and can drive dashboards and
  queries.
- Forward-only: pagares already classified keep whatever `PresenceOnlyPydantic` captured until
  they are re-extracted. Decide backfill separately.

### 2. Verdict deadline tracking  — BACKEND DONE 2026-08-31

- An organization sets a default number of days allowed before a verdict must be made, and an
  individual credit case can override it.
- Surfaces as days passed / days remaining, so a reviewer can see which cases are running out
  of time.
- Backend only for now. `CreditCase` already carries `assigned_to`, `submitted_at`,
  `verdict_at` and `requirements_completed_at`, so the timestamps this builds on exist.

### 3. Labels as org-scoped filters  — DONE 2026-08-31 (backend was already complete)

- Users filter and track credit cases by their own labels (e.g. `sucursal`).
- The BACKEND FOR THIS IS ALREADY COMPLETE: `Label` / `LabelValue` models, both viewsets,
  organization scoping, and `custom_fields` on `CreditCaseSerializer` — already prefetched in
  `CreditCaseViewSet.queryset`, so there is no N+1 to fix.
- The frontend shipped 2026-08-31: `/labels` creates, renames and deletes a field;
  `CustomFieldsPanel` sets its value on a credit case; each field is a filterable, sortable
  dashboard column. See `docs/architecture/decisions.md` > "A user-created field is just
  another table column", and
  `logs/implementations/v2_frontend_labels_and_deadlines-2026-08-31-19-42-27.md`.
- Note for whoever picks this up next: creating a field does NOT backfill existing credit
  cases — they read as "—" until someone fills them in. That is deliberate, and documented
  on the page itself.

### 4. Credit Case Summary Detail

Its own milestone, deliberately NOT part of the first pass.

- When a case's data is complete, generate a summary of the details that actually matter for a
  human making the final verdict.
- Note before starting: `GPTService.run_gpt_loan_verdict()` looks like a head start and is not.
  It is legacy from a consumer-LOAN product — it returns loan amount, annual interest rate,
  monthly payment and term months, none of which describe trade credit. Its only call site is
  commented out, `CREDIT_CASE_AI_VERDICT_ENABLED` is `False`, and it reads
  `credit_case.buro_de_credito_reports`, a relation that lives on `AccountApplication` and not
  on `CreditCase`, so calling it would raise `AttributeError`. Reuse the OpenAI call shape;
  rewrite the schema.
- The real cost here is prompt iteration to reach a genuinely useful summary, not code.

### 5. Frontend UI Views (this iteration)  — DONE 2026-08-31

- Dashboard columns: expose user-owned labels as columns that filter and sort like built-in
  ones (e.g. label `sucursal`), plus days passed / days remaining from item 2.
- `CreditCaseTable.tsx` already drives its header, filter and sort pipelines from one
  declarative `COLUMNS` array, and already supports a `relativeDays` filter kind, so both fit
  the existing shape. The one structural change is that `COLUMNS` is a module-level constant
  and must become dynamic to hold per-organization label columns.
- Stretch: CSV export of the current dashboard view. The filtered rows are already in the
  browser, so this is a client-side download. Excel and PDF are a different job - see v3.
- Shipped: `COLUMNS` became `buildColumns(labels)`, and the table BODY moved onto the same
  array (each column owns a `renderCell`) — a fixed body would have put values under the
  wrong headings the moment the column list changed. Added "Days open" and "Days left"
  columns with a new `deadlineBuckets` filter kind, and the CSV export of `visibleRows`.

### Known ceiling

The credit case dashboard filters and sorts ENTIRELY IN THE BROWSER (`credit-cases/page.tsx`
says so outright). That is fine at current volumes and it is exactly why items 2, 3 and 5 are
cheap. It is also the reason the analytics and documents-dashboard items are in v3: both need
server-side filtering first.

## User-created file types

Deferred out of v1 on 2026-08-11. What SHIPPED in v1: an organization builds its own requirement
templates (strictly-required vs optional, set a default, add/remove per customer) — but only from the
app-provided catalog of file types. See `docs/architecture/decisions.md` > "Document requirements".

What is still MISSING is the ability to invent a file type that isn't in that catalog, e.g. typing
"Carta de poderes" when the app has never heard of it.

The v1 architecture was built so this is an addition, not a rewrite:

- `storage.FileType.organization` is already nullable. `NULL` = app-provided/global; set = that
  organization's own. Creating an org-owned type is a new ROW and can never modify a global one.
  `unique(organization, key)` plus a partial unique index on `key WHERE organization IS NULL` already
  keep both namespaces clean.
- `UploadDocument.file_type_name` is already a plain `CharField` with no `choices`, so an
  organization-specific key stores fine.
- The GPT classifier's allowed-values schema is already built per request rather than at import
  (`GPTService.get_file_type_name_json_schema`).
- Requirement templates already reference `FileType` by FK, so a custom type slots in with no
  special-casing.

Remaining work, roughly in order:

1. Make `FileTypeViewSet` writable for org-owned rows. Slugify `key` from the user's label; enforce
   immutability after create (documents are stored under it).
2. Add an `extraction_schema` JSONField to `FileType`. NOTE: `gpt.py` passes a JSON Schema to OpenAI
   structured outputs and only uses pydantic to GENERATE one — so a custom type can store JSON Schema
   directly. No runtime `create_model()` / code generation is needed. Resolution becomes:
   `spec.pydantic_model.model_json_schema()` for globals, the stored schema for custom ones.
3. Thread the organization through `get_file_type_name_json_schema()` so classification offers
   global + that org's keys.
4. Decide the shadowing rule: what happens when an org owns `carta_de_poder` and the app later ships
   a global type with the same key (org wins / merge / rename-on-conflict). Deliberately left open.
5. Frontend: `GET /file-types/` returns globals and the org's own in one list, custom ones badged; the
   template editor gets an "+ Add custom requirement" flow (name + the fields to extract).

Degrades gracefully in the meantime: the friendly-file-name `if/elif` chain in
`storage/services/db_object_handling.py` won't match a custom type, so `friendly_file_name` just stays
null rather than erroring.

## Candidate file types for the catalog

**See `docs/architecture/file_type_catalog_reference.md`** — the full set of document types relevant
to Mexican trade credit, with a Status column marking which shipped in v1 and which were deliberately
deferred here. That file also records why each deferred row exists, so nothing needs re-deciding when
it is picked up.

Adding a deferred type is: move its row into `core/file_type_catalog.py` as one `FileTypeSpec`
(plus a pydantic extraction model, unless it is presence-only), then `manage.py sync_file_types`.

Deferred to v2, grouped as in that file:

	- Financial: estados financieros dictaminados / internos, carátula de estado de cuenta,
	  antigüedad de saldos CxC y CxP, relación de deuda, proyecciones financieras,
	  relación de activos fijos, estado financiero personal, cédula profesional del contador
	- Tax: alta en Hacienda (R1), cédula de identificación fiscal
	- Legal: folio mercantil (RPPC), comprobante de domicilio comercial, declaración de beneficiario controlador
	- Credit: solicitud de crédito, autorización de consulta a Buró, reporte de Buró,
	  referencias bancarias, aviso de privacidad, contrato de crédito
	- Collateral: escritura del inmueble, certificado de libertad de gravamen, avalúo,
	  póliza de seguro, inscripción en el RUG
	- Operational: orden de compra / contrato de suministro

Also carried forward from that file, and NOT solved by adding catalog rows:

	- per-person requirements (one ID per aval / beneficial owner) — a `quantity` field on
	  `CreditCaseRequirement`, since completion currently compares SETS of file type keys
	- enforcing `months_required` — `CreditCase.missing_file_type_names` ignores it today
	- equivalence groups — dropped from v1 because both `registro_fiscal` alternatives
	  (R1, cédula de identificación fiscal) are deferred, leaving a one-member group.
	  Revisit when either lands.
	- the Buró consent gap — `carta_autorizacion_buro` is deferred while
	  `BURO_DE_CREDITO_REJECTED` and the integration already exist
	- a display field for UI grouping — `category` cannot carry it, it means recency
